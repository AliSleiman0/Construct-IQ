# 14. Database Modeling Rules

Use a relational model with normalized tables.

## Use relations for

* organizations and users
* projects and project members
* projects and phases
* projects and milestones
* projects and tasks
* tasks and dependencies
* daily reports and report entries
* budgets and budget lines
* purchase orders and purchase order items
* suppliers and purchase orders
* documents and related entities

## Use JSONB columns only when needed for flexible metadata

Examples:

* AI prompt metadata
* audit log metadata
* optional document metadata
* assistant response context snapshots

## Main rules

* prefer normalized tables
* use foreign keys
* enforce unique constraints
* use join tables for many-to-many relationships
* use enums for stable statuses and categories
* use JSONB only for flexible fields, not core business structure

# 16. Multi-Tenant Design

This platform must be multi-tenant from day one.

## Rules

Every major table should contain:

* `organization_id`
* `project_id` where applicable

This gives:

* clean data isolation
* faster filtering
* easier permission checks

Examples:

* a user belongs to one organization
* a project belongs to one organization
* a task belongs to one project and one organization

## Recommendation

Use application-level tenant isolation with strict query scoping by `organization_id`.

# 28. AI Feature Plan for MVP

Do not overbuild AI first. Start with 3 useful AI capabilities.

## 28.1 AI Daily Report Summary

When a daily report is submitted:

1. save the report and related rows
2. enqueue a background job
3. collect report data
4. send structured prompt to LLM
5. save generated summary in report

## 28.2 AI Weekly Project Summary

Every week or on demand:

1. collect tasks completed
2. collect open issues
3. collect budget changes
4. collect delayed items
5. generate short executive summary

## 28.3 AI Assistant

User asks:

* what tasks are delayed
* summarize this project
* what risks are active
* what deliveries are late

Assistant flow:

1. validate access to project
2. fetch structured project data
3. optionally fetch related docs later
4. build safe prompt
5. return concise answer
6. store chat history

# 29. Rule-Based Risk Engine Plan

Start with rules before machine learning.

## Delay rules

* due date passed and status not done
* task dependency delayed
* report blockers repeated multiple days

## Cost rules

* actual spend exceeds planned threshold
* purchase orders spike unexpectedly

## Procurement rules

* expected delivery date passed and not delivered
* too many pending purchase orders

## Output

Create AI insight records with:

* type
* severity
* title
* message
* recommendation
* project_id
* organization_id

# 37. PostgreSQL Indexing Plan

Create indexes early.

## Important indexes

### Users

* unique index on `email`
* index on `organization_id`

### Projects

* index on `organization_id`
* index on `status`

### Tasks

* index on `project_id`
* index on `organization_id`
* index on `status`
* index on `assigned_to`
* index on `due_date`
* composite index on `(project_id, status)`
* composite index on `(organization_id, project_id)`

### Daily Reports

* index on `project_id`
* index on `report_date`
* composite index on `(project_id, report_date desc)`

### Issues

# 51. Prisma and PostgreSQL Implementation Notes

## Prisma setup

Install:

```bash
npm install prisma @prisma/client
npm install -D prisma
```

Initialize:

```bash
npx prisma init
```

## Database URL

Use in `.env`:

```env
DATABASE_URL="postgresql://USER:PASSWORD@HOST:5432/DB_NAME?schema=public"
```

## Recommended Prisma workflow

* define models in `prisma/schema.prisma`
* run migrations with `npx prisma migrate dev`
* generate client with `npx prisma generate`
* use PrismaService in NestJS for DB access

## Recommended relation strategy

### one-to-many

* organization → users
* project → tasks
* project → daily reports
* supplier → purchase orders

### many-to-many

* users ↔ roles
* roles ↔ permissions
* users ↔ projects through `project_members`

## Recommended enum usage

Use PostgreSQL / Prisma enums for stable values such as:

* project status
* task status
* task priority
* issue severity
* issue type
* purchase order status
* delivery status
* document type

## Recommended timestamp fields

Add these to all major tables:

* `created_at`
* `updated_at`

Add these where needed:

* `deleted_at` for soft delete
* `created_by`
* `updated_by`

## Recommended constraints

* unique email per user
* unique PO number per organization if needed
* one budget per project
* prevent duplicate project member rows with composite unique constraints
* prevent duplicate task dependency pairs

## Recommended transaction usage

Use Prisma transactions for flows like:

* creating purchase order with items
* creating budget with budget lines
* creating daily report with manpower and material rows
* assigning project members in bulk

## Recommended soft delete strategy

Use `deleted_at` for entities that may need recovery, such as:

* projects
* tasks
* issues
* suppliers
* documents

Avoid hard delete for critical business records.

# 52. Relational Design Adjustments by Module

## Tasks

Tasks need:

* `tasks` table
* `task_dependencies` table instead of dependency arrays

## Daily Reports

Daily reports should use:

* `daily_reports`
* `daily_report_manpower_entries`
* `daily_report_material_entries`

This is better for reporting, filtering, and analytics.

## Budgets

Budgets should use:

* `budgets`
* `budget_lines`

This makes totals and variance easier to query.

## Purchase Orders

Purchase orders should use:

* `purchase_orders`
* `purchase_order_items`

Deliveries stay separate and reference purchase orders.

## Roles and Permissions

Use proper many-to-many structure:

* `roles`
* `permissions`
* `user_roles`
* `role_permissions`

This is better than storing permission arrays in a single record.
